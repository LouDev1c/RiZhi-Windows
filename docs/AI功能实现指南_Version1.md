# 日织 AI 功能实现指南（Version 1）

## 1. 文档目标

本文档用于把日织 AI 功能的最终形态拆成可独立开发、验证和回退的阶段。每个阶段都明确：

- 本阶段解决什么问题；
- 要修改哪些模块；
- 什么内容暂时不做；
- 开发者如何自动验证；
- 产品负责人如何手动验收和补充遗漏。

Version 1 的最终范围包括：

1. 记录页：文本润色、日记续写、根据任务和媒体注释生成日记。
2. 统计页：日报、周报、月报、季报和年报。
3. 设置页：日织提供的会员模型与用户自备 API 两种模式。
4. 媒体素材：用户可以为图片、视频标注事件时间、事件内容、关联任务和是否允许 AI 使用。

明确不包含：记录页“日记总结”。总结能力统一由统计页的周期报告承担。

## 2. 不可破坏的产品原则

### 2.1 用户控制

- AI 输出必须先进入可编辑预览。
- 未经用户确认，不得覆盖日记、修改任务状态或保存报告。
- “覆盖原文”必须支持现有撤销逻辑；“添加到原文”应保持合理换行。
- 用户可以取消正在进行的请求，并在失败后继续编辑原内容。

### 2.2 数据真实性

- 任务数量、完成率、分类和计划时长由本地代码计算，模型只负责分析和表达。
- 计划时长不得表述为实际投入时长。
- 用户填写的任务完成状态是唯一状态来源，媒体注释不能自动改变它。
- 时间线冲突应被提示或用中性语言表达，AI 不得自行选择“真实版本”。
- 数据不足时必须说明不足，不得补造人物、地点、事件、情绪或原因。

### 2.3 隐私与安全

- V1 默认只向模型发送文字和结构化数据，不发送图片、视频二进制及本地文件路径。
- 每次生成前应让用户知道将使用哪些类型的数据。
- API Key 只在 Electron 主进程使用，通过 `safeStorage` 加密保存。
- preload 不得向渲染进程返回 API Key、会员令牌或模型服务原始错误体。
- 日织自有模型必须经日织服务端代理，客户端不得包含开发者的模型密钥。

### 2.4 架构边界

```text
页面交互
  -> preload 白名单接口
  -> main IPC 与权限检查
  -> AI feature
  -> 本地上下文 / 时间线 / 提示词 / 响应校验
  -> Provider 适配器
  -> 模型服务
```

- `src/media` 管理媒体注释这一基础数据。
- `src/ai` 管理 AI 业务用例和上下文。
- `src/modelProviders` 管理模型服务调用差异。
- 渲染进程不得直接调用外部模型 API。

## 4. 分阶段实施与验收

### 阶段 0：固定范围与代码骨架

目标：先统一跨层命名、目录职责和实施规则，不改变现有软件行为。

实施内容：

- 建立 `src/ai`、`src/media`、`src/modelProviders` 目录说明。
- 定义三种日记动作：`polish`、`continue`、`compose`。
- 定义五种报告周期：`day`、`week`、`month`、`quarter`、`year`。
- 定义两种模型来源：`managed`、`byok`。
- 定义统一请求状态和错误码。
- 为契约增加单元测试并纳入项目检查命令。

自动核验：

- 新增 JavaScript 文件通过 `node --check`。
- `tests/aiContracts.test.js` 验证枚举值和被删除的 `summarize` 动作。
- 运行现有完整测试，确认无行为回归。

产品验收：

- 确认记录页只有润色、续写、素材成文。
- 确认日报属于统计页。
- 确认模型来源的命名和产品概念一致。

完成标准：目录、契约、指南和测试都进入仓库，现有软件功能不变。

### 阶段 1：结构化媒体注释与数据兼容

目标：让媒体注释成为 AI 和用户都能使用的可靠基础数据。

实施内容：

- 保留现有 `annotation` 自由文本。
- 为媒体条目新增 `timeline.eventTime`、`eventTitle`、`relatedTaskId`、`includeInAi`。
- 增加规范化与校验函数，兼容没有 `timeline` 的旧数据。
- 扩展媒体注释界面，提供时间、标题、说明、关联任务和 AI 使用开关。
- 关联任务下拉框只列出该记录日期的任务。
- 删除任务后保留媒体注释，但将失效关联显示为“原关联任务已不存在”。

暂不实施：图片识别、视频内容识别、自动读取并发送媒体文件。

自动核验：

- 旧媒体数据加载、保存后不丢失。
- 非法时间、非布尔开关、失效任务 ID 能被规范化或明确标记。
- 媒体存储迁移和现有本地数据测试继续通过。

产品验收：

- 分别测试图片、动态图片和视频注释。
- 测试不填写时间、不关联任务以及关闭 AI 使用开关。
- 重启软件后字段仍然存在。
- 检查旧附件仍可正常查看、编辑和删除。

完成标准：媒体注释可以独立使用，即使没有配置 AI 也完整可用。

### 阶段 2：确定性时间线引擎

目标：在调用模型前，由本地程序完成排序、匹配和冲突发现。

实施内容：

- 将任务、任务状态、任务备注和媒体事件合并成当日时间线。
- 匹配优先级：用户明确关联任务 > 时间落入单个任务 > 未确定。
- 检测媒体事件与任务重叠、多个候选任务、缺失时间和失效任务引用。
- 产出稳定的时间线 DTO，不改变原任务或媒体数据。
- 在开发期提供可读的时间线预览，便于人工验证。

自动核验：

- 覆盖无任务、单任务、重叠任务、跨日任务、无时间素材和多个素材等测试。
- 同一输入始终生成相同顺序和相同冲突结果。
- 时间线构建不修改输入对象。

产品验收：

- 用一天的真实示例逐项对照任务、注释和输出时间线。
- 重点检查任务首尾时间、相同时间点和跨日边界。
- 对所有“不确定”项确认系统没有替用户下结论。

完成标准：不调用模型也能得到可信、可解释的当日时间线。

### 阶段 3：AI 核心、BYOK 设置与安全 IPC

目标：建立第一条真实但不写入业务数据的模型调用链。

实施内容：

- 实现 Provider 注册与统一调用接口。
- 首先实现 OpenAI 兼容的 BYOK Provider。
- 在设置页增加服务地址、模型名、API Key、超时和连接测试。
- 使用 `safeStorage` 保存密钥，普通设置只保存非敏感项。
- 增加主进程 IPC、preload 白名单、请求取消、超时和错误映射。
- 连接测试只发送最小请求，不读取任何日记数据。

暂不实施：会员支付、日织服务端、流式输出、多模态文件上传。

自动核验：

- 用 Mock Provider 验证选择、超时、取消和错误映射。
- 验证 preload API 不返回密钥。
- 验证日志和错误对象不包含 Authorization Header。
- 无配置、错误 Key、限流、超时和无网络都有稳定错误提示。

产品验收：

- 保存设置、重启、连接测试成功。
- 切换到错误配置后能看到易懂提示，原数据不受影响。
- 界面仅显示 API Key 已配置状态，不能重新读出完整密钥。

完成标准：BYOK 可以安全测试连接，但还不会自动改写日记。

### 阶段 4：文本润色与日记续写

目标：交付第一个用户可感知的 AI 闭环。

实施内容：

- 实现润色和续写上下文、提示词及响应校验。
- 记录页增加 AI 操作入口、进行中状态和取消按钮。
- 建立共用结果编辑窗口。
- 支持重新生成、添加到原文、覆盖原文和取消。
- 接入未保存状态与撤销逻辑。
- 润色时约束模型不改事实；续写时禁止补造未提供的事件。

自动核验：

- 空文本、超长文本、特殊字符、模型空响应和取消请求都有测试。
- 确认生成结果在用户点击前不会写入 `journals`。
- 覆盖和添加后，保存、撤销、切换日期的原有行为正确。

产品验收：

- 使用短日记、长日记、口语化日记分别测试。
- 检查原文中的日期、人物、数字和否定含义是否被改变。
- 生成后手动编辑结果，再测试添加和覆盖。
- 请求失败时原文必须完整保留。

完成标准：用户可安全完成“选择操作—生成—编辑—采用—保存”。

### 阶段 5：素材成文

目标：根据任务与媒体注释双向整理时间线，产出可编辑日记草稿。

实施内容：

- 接入阶段 2 的时间线结果。
- 生成前展示本次使用的任务数、媒体注释数和冲突数。
- 对有歧义的时间线允许用户返回修改注释，或确认继续生成。
- 提示词区分计划、已完成、部分完成、未完成和未确认。
- 生成结果支持添加或覆盖，不自动保存。
- 保存最小生成来源信息，用于后续解释报告数据来源；不保存密钥和完整请求体。

自动核验：

- `includeInAi: false` 的素材绝不进入模型上下文。
- 上下文不包含本地媒体路径和媒体二进制。
- 冲突和未定时事件能稳定传给提示词层。
- Mock 模型下可以完整走通预览、编辑和采用流程。

产品验收：

- 准备“任务与素材一致”“部分重叠”“明显冲突”三组案例。
- 检查成文是否区分“计划做”和“确认完成”。
- 检查没有注释的图片不会被 AI 猜测内容。
- 检查关闭 AI 使用开关的素材没有出现在结果中。

完成标准：素材成文可用，且每句话都能追溯到用户提供的文字或结构化状态。

### 阶段 6：日报与周期报告

目标：在统计页生成有数据依据的日、周、月、季、年复盘。

实施内容：

- 先由本地代码计算任务数量、状态分布、分类和计划时长。
- 构建报告上下文，附加日记、任务备注、标签和媒体事件摘要。
- 先完成日报，再复用同一管线扩展周、月、季、年。
- 报告包含概览、进展、偏差、问题和下一周期建议。
- 增加报告编辑、重新生成、保存、复制和来源更新时间提示。
- 使用 `sourceFingerprint` 判断报告生成后源数据是否发生变化。
- 报告单独保存，不混入普通日记列表。

自动核验：

- 各周期边界与现有统计页保持一致，尤其是自然周和季度。
- 本地计算结果与现有统计数字逐项一致。
- 空周期、少量数据、跨月周、跨年周都有测试。
- 日记中的描述不会被二次计算为任务完成数量。

产品验收：

- 对照统计页手工核对报告中的数字。
- 修改周期内一项任务后，旧报告应提示数据已更新。
- 检查建议是否具体但没有虚构原因。
- 检查月报、季报、年报的篇幅和信息层次是否合理。

完成标准：五种报告共享统一管线，数字可靠，文本可编辑和保存。

### 阶段 7：日织会员模型

目标：在不暴露开发者密钥的前提下提供日织托管模型。

客户端实施内容：

- 实现 `managedProvider`。
- 增加登录状态、会员状态、额度和续费入口。
- 设置页支持在日织模型与 BYOK 之间切换。
- 明确展示当前请求将使用哪种服务和是否计费。

服务端前置内容：

- 用户认证与令牌刷新。
- 会员、订单和支付回调。
- 模型代理、配额、限流、审计和滥用防护。
- 隐私政策、数据保留策略和用户删除机制。

自动核验：

- 未登录、非会员、额度不足、令牌过期和服务不可用均有测试。
- 客户端安装包中不存在开发者模型密钥。
- 服务端只接受经过认证和授权的请求。

产品验收：

- 会员和 BYOK 切换后调用来源、额度展示和错误文案正确。
- 会员到期不会影响用户继续读取本地日记和历史报告。
- 付费动作前价格、权益和消耗规则清楚可见。

完成标准：托管模型具备完整账户、计费、安全和故障处理闭环，而不是仅能调用一次接口。

### 阶段 8：发布前加固

目标：将功能从“可用”提升到适合正式发布。

实施内容：

- 请求长度、并发、重试和速率限制。
- 敏感日志清理与崩溃恢复。
- 数据发送说明、首次授权和隐私设置。
- 提示词版本、上下文版本和报告数据版本记录。
- 取消、关闭窗口、休眠恢复和网络切换处理。
- 更新 README、技术说明文档和用户教程。

核验：

- 执行完整自动测试、打包测试和旧版本数据升级测试。
- 使用脱敏的极端长度数据进行稳定性测试。
- 检查安装包、日志、设置文件和错误报告中没有明文密钥。
- 完成一次从旧版本安装、升级、生成、卸载的完整人工流程。

完成标准：隐私、安全、兼容、异常恢复和文档均达到发布要求。

## 5. 每个阶段的统一工作流程

每一阶段都按以下顺序执行：

1. 在本指南确认范围和非目标。
2. 先写数据契约和测试案例，再实现业务。
3. 完成纯函数和存储层，再接 IPC。
4. 完成 IPC 后再做页面交互。
5. 运行 `npm run check`。
6. 开发者按该阶段“自动核验”提交结果。
7. 产品负责人按“产品验收”检查，并把遗漏补充回本指南。
8. 只有当前阶段完成标准满足后，才进入下一阶段。
